# Recommendation Explainability Contract

## 1. Core Principle
Every recommendation generated by Ishkeen must be strictly and deterministically explainable. We must prevent internal implementation details from bleeding into user-facing copy while ensuring that every decision can be traced back to its exact provenance (User, Model, or Policy).

## 2. Separation of Concerns
The engine will separate the explanation into three layers:
1. **Machine Reason Code**: Stable, deterministic strings representing the architectural trigger (e.g., `SENSITIVITY_COMPLEXITY_LIMIT`).
2. **Structured Explanation Parameters**: Contextual data attached to the reason code (e.g., `{"candidate": "aha_acids", "trigger_value": "high_sensitivity"}`).
3. **Presentation Copy**: The frontend UI layer responsible for mapping the Reason Code and Parameters into editorial, user-friendly text. The backend does NOT send raw strings like "We excluded AHAs because you have high sensitivity" to allow for I18N and UI flexibility.

## 3. Standard Reason Codes

### Goal & Concern Codes (Why a candidate was proposed)
- `GOAL_SUPPORT_BREAKOUTS`
- `GOAL_SUPPORT_HYDRATION`
- `CONCERN_TARGET_UNEVEN_TONE`

### Exclusion & Safety Codes (Why a candidate was removed/deferred)
- `EXCLUDED_KNOWN_REACTION`: Removed due to a hard user-reported reaction.
- `EXCLUDED_USER_PREFERENCE`: Removed due to explicit user avoidance preference.
- `CONSERVATIVE_CLINICIAN_CARE`: Deferred to avoid interfering with prescribed treatment.
- `SENSITIVITY_DOWNGRADE`: Removed/swapped for a gentler alternative due to high sensitivity.
- `COMPLEXITY_LIMIT_ENFORCED`: Deferred because the routine would exceed the beginner/familiar active cap.
- `ALREADY_USING_CATEGORY`: Not recommended as a new addition because the user already uses it.
- `SUNSCREEN_FOUNDATION_REQUIRED`: Photosensitizing active deferred until sunscreen usage improves.

### Model Integration Codes (Future)
- `EVIDENCE_USER_REPORTED`: The primary driver was the questionnaire.
- `EVIDENCE_MODEL_DETECTED`: The primary driver was the image analysis.
- `EVIDENCE_USER_REPORTED_MODEL_CLEAR`: The user reported a concern, but the model did not detect it (User truth prioritized).
- `STALE_MODEL_EVIDENCE_IGNORED`: Model data existed but was dropped due to age.

## 4. LLM Explanation Boundary (Future)
If an LLM is used to verbalize the structured output in Phase 6B or beyond:
- The LLM **receives** the finalized, deterministic structured recommendation and explanation codes.
- The LLM **cannot** add new ingredients, remove safety exclusions, diagnose conditions, or suggest specific product concentrations.
- **Validation**: Any LLM output must be constrained to presentation-only transformation. If the LLM generates an explanation that contradicts the deterministic codes (e.g., mentioning BHA when the deterministic output excluded it), the system must fallback to template-based explanations. MVP will exclusively use template-based explanations.
